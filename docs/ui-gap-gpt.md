# UI gap audit: Stroll vs ChatGPT/Codex desktop conventions

Scope: motion, micro-interaction, and layout gaps only. Static chrome (Paper light theme, serif
prose option, composer card, thin-ring spinners, menus/comboboxes/sheets, sidebar brand row,
tool-call activity row) is out of scope and already lands close to target — see "Do not change."

## Verdict

Stroll's static chrome is close to the ChatGPT/Codex target — cards, spacing, menu shape, and
color are already tuned. What is missing is almost entirely motion: new turns, tool-call rows, and
message containers pop into existence with no transition; the composer's height, the sidebar's
collapse, and the send button's icon swap all resize or swap instantly instead of easing; icon
tooltips fire with zero delay everywhere instead of the target's deliberate short delay; and there
is no empty-state hero (greeting + suggestion chips) on New chat, so it reads as a blank form
rather than a landing moment. The app already has one working motion primitive worth generalizing:
`react-native-reanimated`'s `FadeIn`/`FadeOut` and a scale-from-0.97 menu-open keyframe are used
correctly in three or four places (scroll-to-bottom pill, tooltip, hover card, combobox panel,
menu overlay) — the fix is applying that same primitive to the rest of the surfaces, not inventing
something new. Reduced-motion support is real but narrow: three components check
`useReducedMotion()` (loading spinner, synced loader, chat outline rail); every other
`FadeIn`/`FadeOut`/shimmer usage, including the ones already "matching" the target, ignores it.

## Motion system (proposal)

Converge on one system so implementers don't invent per-component motion:

1. **Library**: `react-native-reanimated` (already a dependency, already used correctly in
   `menu-overlay.tsx`, `tooltip.tsx`, `workspace-hover-card.tsx`, `combobox.tsx`,
   `agent-stream/view.tsx`). Do not add a second animation library.
2. **Tokens**: add a `motion` block to `packages/app/src/styles/theme.ts` alongside the existing
   `spacing`/`radius`/`opacity` scales — e.g. `duration: { fast: 100, base: 150, slow: 200 }` and
   `easing: { out: Easing.out(Easing.cubic) }` (or the exact curve already used by
   `CONTENT_ENTERING_DURATION_MS` in `menu-overlay.tsx:44`, promoted to a shared constant instead
   of a local one).
3. **Reduced motion gate**: one shared `useAppReducedMotion()` wrapping reanimated's
   `useReducedMotion()`, imported everywhere an `entering`/`exiting`/`withTiming` call is added or
   touched — including the three components that already call the raw hook, so there's one seam to
   change if the check ever needs augmenting (e.g. an app-level "reduce motion" setting layered on
   top of the OS setting).
4. **Pattern to copy**: `menu-overlay.tsx:44-54`'s `entering`/`exiting` keyframe pair
   (scale 0.97→1 + opacity, 150ms) is the reference shape for "open/close" motion; `agent-stream/
view.tsx:452-457`'s `FadeIn`/`FadeOut.duration(200)` is the reference for "appear/disappear in
   place" motion (scroll pill, future message entrance). New motion should be one of these two
   shapes, not a third.
5. **Do not** replace `LayoutAnimation` or RN's `Animated` API anywhere — this codebase has
   already standardized on reanimated; the only other animation API present (`Animated.Value` in
   `toast-host.tsx`, `sidebar-agent-list-skeleton.tsx`, `pull-request-panel/activity-skeleton.tsx`)
   is legacy skeleton/toast code, not a competing system to reconcile against this audit's scope.

## Method notes

- Reduced-motion, focus-trap, and attachment-chip claims marked "not independently re-verified"
  above are code-read only; a live confirmation pass would strengthen them but was out of budget
  for this audit.
- Live hover states (sidebar row kebab, assistant message hover) could not be captured as
  screenshots: headless Chromium via `abx` has no real pointer, and dispatching synthetic
  `pointerenter`/`pointerover`/`mouseover` events on the DOM node did not trigger React Native
  Web's hover state for these specific components (it did work implicitly for menu/tooltip opens
  triggered by `click`). Those findings rely on direct code reads instead, which is more precise
  for citation purposes ("what to change") even though it forgoes a screenshot.
- `/tmp/stroll-ui-reference.jpg` (the OpenClaw/Codex-style reference mentioned in the task) did not
  exist on disk at audit time; this audit judged against the ChatGPT/Codex desktop conventions
  listed in the task prompt instead.
- The main workspace/chat surface and the Settings surface can independently resolve
  System-theme to different light/dark values on cold load (observed once: chat rendered dark
  while Settings rendered light, both under Theme = System). Not chased down — flag for a
  follow-up if reproducible, out of scope for this motion audit.
